# Social Recovery Module SDK Reference

abstractionkit ships one class per Social Recovery Module version. Use `SocialRecoveryModuleV2` (module v0.2.0) for new integrations, and `SocialRecoveryModuleV1` (module v0.1.0) for accounts that already enabled v0.1.0.

:::

## Choose a Module Version

Social Recovery Module v0.2.0 fixes the findings of [Certora's audit](https://github.com/candidelabs/candide-contracts/releases/tag/recovery%2Fv0.2.0) and is a new deployment with new addresses. v0.1.0 stays deployed. Each version has its own class and grace period selector:

| Module version | Class | Grace period selector | Recovery request type |
|---|---|---|---|
| v0.2.0 (recommended) | [`SocialRecoveryModuleV2`](https://github.com/candidelabs/abstractionkit/blob/v1.0.0/src/account/Safe/modules/SocialRecoveryModule.ts#L559) | `SocialRecoveryModuleGracePeriodSelectorV2` | `RecoveryRequestV2` |
| v0.1.0 | [`SocialRecoveryModuleV1`](https://github.com/candidelabs/abstractionkit/blob/v1.0.0/src/account/Safe/modules/SocialRecoveryModule.ts#L691) | `SocialRecoveryModuleGracePeriodSelectorV1` | `RecoveryRequestV1` |

:::warning Accounts on v0.1.0 must stay on V1
Pick the class that matches the module your accounts enabled. If your users enabled the v0.1.0 module, use `SocialRecoveryModuleV1` and `SocialRecoveryModuleGracePeriodSelectorV1`. Pointed at a v0.2.0 address, an account that enabled v0.1.0 has no guardians, and its recovery calls fail.

`SocialRecoveryModuleV1` and `SocialRecoveryModuleGracePeriodSelectorV1` are what `SocialRecoveryModule` and `SocialRecoveryModuleGracePeriodSelector` were before abstractionkit v1.0.0, with the same addresses.
:::

### V1 vs V2 Differences

| | V1 (module v0.1.0) | V2 (module v0.2.0) |
|---|---|---|
| `createConfirmRecoveryMetaTransaction` | `(accountAddress, newOwners, newThreshold, execute)` | `(accountAddress, newOwners, newThreshold, nonce, execute)` |
| `createMultiConfirmRecoveryMetaTransaction` | `(accountAddress, newOwners, newThreshold, signaturePairList, execute)` | `(accountAddress, newOwners, newThreshold, nonce, signaturePairList, execute)` |
| Guardian signature EIP-712 domain version | `"0.0.1"` | `"0.2.0"`. Signatures made for v0.1.0 are not valid on v0.2.0. |
| `getRecoveryRequest` returns | `RecoveryRequestV1` with `executeAfter` | `RecoveryRequestV2` with `nonce` and `executableAt` |
| Adding or revoking a guardian, changing the threshold | Leaves a recovery in progress untouched | Cancels the recovery in progress and invalidates the guardian confirmations collected so far |
| `cancelRecovery` | Reverts when no recovery is in progress | Also invalidates collected confirmations, and works when no recovery is in progress |
| New owners | Validated at finalization | Also validated at confirmation and execution. For example, confirming a recovery that names a guardian as a new owner reverts. |
| `hasGuardianApproved` | Can report an approval from an address that is no longer a guardian | Reports approvals from current guardians only |

On V2, pass the recovery nonce the guardians signed to the confirm methods. Read it from `messageValue.nonce` returned by [`getRecoveryRequestEip712Data`](#getrecoveryrequesteip712data), or call [`nonce`](#nonce) for a single guardian confirming on-chain. The module reverts with `SM: invalid nonce` if the nonce changed before the transaction is included.

### SocialRecoveryModuleBase

[`SocialRecoveryModuleBase`](https://github.com/candidelabs/abstractionkit/blob/v1.0.0/src/account/Safe/modules/SocialRecoveryModule.ts#L51) is the abstract class both versions extend. It holds every method the two versions share: guardian management, execute, finalize, cancel, the read helpers, and `getRecoveryRequestEip712Data`. Use it as a type for code that accepts either version. The confirm methods and `getRecoveryRequest` differ between versions, so they live on `SocialRecoveryModuleV1` and `SocialRecoveryModuleV2`.

```ts
import { SocialRecoveryModuleBase } from "abstractionkit";

async function listGuardians(srm: SocialRecoveryModuleBase, nodeUrl: string, accountAddress: string) {
  return srm.getGuardians(nodeUrl, accountAddress);
}
```

## Initialize

Initialize a `SocialRecoveryModuleV2` instance. By default, the grace period for recovery is set to 3 days.

```ts
const srm = new SocialRecoveryModuleV2(); // 3 days
```

If you need a different grace period, you can override it by providing
a [different grace period address](/wallet/technical-reference/deployments/#social-recovery-module)
during initialization.

```ts
import { SocialRecoveryModuleV2, SocialRecoveryModuleGracePeriodSelectorV2 } from "abstractionkit";

const gracePeriod = SocialRecoveryModuleGracePeriodSelectorV2.After7Days;
const srm = new SocialRecoveryModuleV2(gracePeriod); // 7 days
```

`SocialRecoveryModuleGracePeriodSelectorV2` offers `After3Minutes`, `After3Days`, `After7Days`, and `After14Days`. The 3-minute deployment is on testnets only.

For accounts that enabled module v0.1.0, use the V1 class with the V1 selector:

```ts
import { SocialRecoveryModuleV1, SocialRecoveryModuleGracePeriodSelectorV1 } from "abstractionkit";

const srm = new SocialRecoveryModuleV1(SocialRecoveryModuleGracePeriodSelectorV1.After3Days);
```

Then consume the module methods like the following:

```ts
const accountAddress = "0x1.."
const guardianAddress= "0x2.."

const metaTransaction1 = srm.createEnableModuleMetaTransaction(accountAddress);

const metaTransaction2 = srm.createAddGuardianWithThresholdMetaTransaction(
    guardianAddress,
    1n //threshold
);
```

## Recover

### createConfirmRecoveryMetaTransaction

Creates a MetaTransaction that lets a single guardian confirm the execution of the recovery request.
It can also trigger the start of the execution by passing true to 'execute' parameter.
Once triggered, the recovery starts the grace period, before it can be finalized.

On V2 it takes the account's current recovery `nonce` before `execute`. Get it with [`nonce`](#nonce).

```ts
// SocialRecoveryModuleV2
const nonce = await srm.nonce(nodeUrl, accountAddress);
const confirmTx = srm.createConfirmRecoveryMetaTransaction(
    accountAddress,
    [newOwnerAddress],
    1, // new threshold
    nonce,
    true, // execute
);
```

### createMultiConfirmRecoveryMetaTransaction

Creates a MetaTransaction that lets multiple guardians confirm the execution of the recovery request.
It can also trigger the start of the execution by passing true to 'execute' parameter.
Once triggered, the recovery starts the grace period, before it can be finalized.
Signature pairs are sorted by signer address for you.

On V2 it takes the recovery `nonce` the guardians signed, before the signatures. Use `messageValue.nonce` from [`getRecoveryRequestEip712Data`](#getrecoveryrequesteip712data). A signature may be empty when its signer is the transaction sender, or when the signer is a Safe guardian that pre-approved the recovery hash (EIP-1271).

```ts
// SocialRecoveryModuleV2
const { domain, types, messageValue } = await srm.getRecoveryRequestEip712Data(
    nodeUrl,
    chainId,
    accountAddress,
    [newOwnerAddress],
    1n, // new threshold
);

// each guardian signs { domain, types, messageValue } and returns { signer, signature }

const multiConfirmTx = srm.createMultiConfirmRecoveryMetaTransaction(
    accountAddress,
    [newOwnerAddress],
    1, // new threshold
    messageValue.nonce,
    signaturePairList,
    true, // execute
);
```
