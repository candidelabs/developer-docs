# Safe Recovery UX API

Use the Recovery UX API to collect guardian signatures, submit recovery transactions, track requests, and manage email/SMS alerts for Safe accounts. It works with the [Social Recovery Module](/wallet/plugins/recovery-with-guardians/) v0.1.0 and v0.2.0.

For email/SMS verification that produces a guardian signature, use the [Email/SMS Recovery API](/wallet/recovery/auth-api/). For an explanation of the full recovery process, see the [service overview](/wallet/recovery/overview/).

## Before You Start

- Enable the Social Recovery Module and configure guardians and a recovery threshold on the Safe account.
- [Request service access](https://app.formbricks.com/s/brdzlw0t897cz3mxl3ausfb5) to obtain your service URL and credential.
- Read the network's modules from [`/v1/config/getNetworkConfig`](#network-configuration) and pass the module the Safe uses as `moduleAddress`. See [Recovery modules](#recovery-modules).
- Use the [Recovery Flow Guide](/wallet/plugins/recovery-flow-guide/) for a TypeScript integration example.

## Authentication

Replace `https://yourcompany.recovery.candide.dev` with your service URL. Every endpoint lives under the `/v1` prefix.

The service is configured with one of two credentials, which you receive with your service URL:

- **Bearer token:** include `Authorization: Bearer YOUR_BEARER_TOKEN` in every request. A missing header is answered with `401 Bearer token required`, a wrong token with `401 Invalid bearer token`, both with a `WWW-Authenticate: Bearer` header. The examples on this page use this form.
- **API key:** the key is the first path segment of every URL, as in `https://yourcompany.recovery.candide.dev/YOUR_API_KEY/v1/recoveries/create`. Any other first segment, including a request that leaves the key out, is answered with `401 Invalid API key`.

Requests that create or approve a recovery also require a **guardian signature** over the recovery hash. Alert subscription management requires an **owner-signed SIWE message**. These signatures authorize the account action; the credential authenticates access to the API.

Examples use placeholder addresses, IDs, messages, and signatures. Replace them with values from your integration. Expressions such as `siwe(...)` and `sign(message)` describe values to generate in your application; they are not literal API inputs.

## Recovery Workflow

1. **Pick the module:** Read the network's modules from `/v1/config/getNetworkConfig` and choose the one the Safe has guardians on.
2. **Create:** Submit a request with the first guardian's signature using `/v1/recoveries/create`, passing that module as `moduleAddress`.
3. **Approve:** Other guardians check the request's emoji sequence with the account owner through a trusted channel, then submit signatures using `/v1/recoveries/sign`.
4. **Execute:** Once the guardian threshold is met, call `/v1/recoveries/execute` to submit the request on-chain and start the grace period.
5. **Finalize:** After the grace period, call `/v1/recoveries/finalize` to apply the new owners and signing threshold. The current owner can cancel the recovery during the grace period.

The service sponsors gas for execution and finalization when configured, but it does not submit them on its own: your application must call both endpoints. Guardians can submit signatures off-chain without holding funds. Use the lookup endpoints to monitor progress; a successful submission does not by itself mean ownership has changed. See [request states](/wallet/recovery/overview/#recovery-request-states).

`newThreshold` is the signing threshold for the **new Safe owners** after recovery. The existing **guardian threshold** determines how many guardians must approve the recovery.

## Recovery Modules

A network can serve several Social Recovery Modules: the v0.1.0 and v0.2.0 versions, each deployed with 3-day, 7-day, and 14-day grace periods, plus 3-minute variants on testnets. A Safe can have more than one enabled while it moves its guardians from v0.1.0 to v0.2.0. A recovery hash, and every guardian signature over it, is valid on one module only because its EIP-712 domain holds the module address. Each recovery flow is therefore bound to one module.

- **Starting a flow:** `/v1/recoveries/create` and [`/v1/auth/signature/request`](/wallet/recovery/auth-api/#request-to-recover-an-account) take an optional `moduleAddress`. It must be one of the network's modules listed by `/v1/config/getNetworkConfig`, otherwise the request fails with a 400. The module is saved on the request.
- **Later steps:** `/v1/recoveries/sign`, `/v1/recoveries/execute`, `/v1/recoveries/finalize`, and `/v1/auth/signature/submit` use the module saved on the request and do not accept `moduleAddress`. Every request response carries its `moduleAddress` and `recoveryHash`.
- **Reads:** `/v1/recoveries/fetchByAddress` and `/v1/recoveries/listByAddress` take an optional `moduleAddress` and return the requests made on that module only. Every module starts each account's recovery nonce at 0, so requests made on different modules can share a nonce.

When `moduleAddress` is omitted, the network's default module is used: the `moduleAddress` returned by `/v1/config/getNetworkConfig`. Pass `moduleAddress` explicitly so the flow runs on the module the Safe has guardians on.

Before a request is created, the service checks that the module is enabled on the Safe and holds guardians for it. When it does not, the error names the problem and asks for the `moduleAddress` of the module that holds the guardians. A `create` signature that is not valid for the default module but is valid for another configured module fails with an error naming that module.

The proposed owners must be ones the module can set: at least one address, no duplicates, and none of the zero address, the sentinel address `0x0000000000000000000000000000000000000001`, the Safe itself, or one of its guardians on that module. The v0.1.0 contract accepts such proposals but can never finalize them, so the service rejects them for both versions.

An empty signature (`0x`) is accepted on v0.2.0 modules only, where it is checked on-chain with EIP-1271 for a Safe guardian that approved the recovery hash. The v0.1.0 contract cannot execute it, so the service rejects it there.

## Endpoints

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET | `/v1/config/getNetworkConfig` | Read a network's modules, sponsorship settings, and alert channels. |
| POST | `/v1/recoveries/create` | Create a request with a guardian signature. |
| POST | `/v1/recoveries/sign` | Add another guardian's signature. |
| POST | `/v1/recoveries/execute` | Submit execution once the guardian threshold is met. |
| POST | `/v1/recoveries/finalize` | Submit finalization after the grace period. |
| GET | `/v1/recoveries/fetchById` | Fetch one request by its service ID. |
| GET | `/v1/recoveries/fetchByAddress` | Fetch requests for an account, chain, and recovery nonce. |
| GET | `/v1/recoveries/listByAddress` | List requests with filters, sorting, and pagination. |
| POST | `/v1/alerts/subscribe` | Create an inactive alert subscription and send a verification code. |
| POST | `/v1/alerts/activate` | Verify the code and activate the subscription. |
| GET | `/v1/alerts/subscriptions` | List active subscriptions for an account and owner. |
| POST | `/v1/alerts/unsubscribe` | Remove a subscription. |

### Create Recovery Request

The `signer` must be a guardian of the Safe account on that module, and `signature` must be the guardian's signature over the module's recovery hash at the account's current nonce. The service stores this first signature with the request.

An account can create one request every 5 minutes per chain; a second attempt within that window is answered with a 429.

### Execute a recovery by ID

Submit the execution transaction for a request that has met the guardian threshold. Execution starts the grace period; it does not change ownership.

The service checks that execution sponsorship is enabled on the network, that the request's nonce is still the account's current nonce on its module, and that enough signatures were collected, then moves the request to `EXECUTION-IN-PROGRESS` and submits the transaction. If the transaction fails, the request returns to `PENDING` and can be submitted again. A second call while a submission is in progress is answered with `403 Execution already pending`; a call for a request that is already executed returns success without a new transaction.

### Finalize recovery by ID

Submit the finalization transaction after the grace period has ended. Once finalized on-chain, the new owners and signing threshold take effect.

The service reads the pending recovery on the request's module: with none it answers 404, and before the grace period ends it answers `403 Recovery request is not yet ready for finalization`. A request executed outside the service can still be finalized through it. If the transaction fails, the request returns to `EXECUTED` and can be submitted again.

## Alerts

Alert subscriptions are separate from email/SMS recovery registrations. Subscribing to alerts does not add a guardian or enable email/SMS recovery.

Create a subscription, then activate it with the code sent to the selected channel. Subscriptions monitor the Safe account across supported chains with alerts enabled. The `chainId` identifies the network used to verify the signing owner. Every alert endpoint checks that `owner` is a current owner of the Safe on that chain, and a subscription belongs to the account, with `owner` recording who created it.

A current owner manages its own subscriptions and those whose creator is no longer an owner, for example after a recovery or an owner swap, but not those of another current owner.

The `owner` signs the SIWE message for subscription creation, lookup, and removal. See [SIWE signing](/wallet/recovery/auth-api/#how-to-sign-messages-siwe-eip-4361) and the [Recovery Alerts Guide](/wallet/plugins/recovery-alerts-guide/).

A Safe that is not deployed yet can subscribe: wrap the owner's signature with ERC-6492 and the Safe's deployment data, as described in [Accounts that are not deployed yet](/wallet/recovery/auth-api/#accounts-that-are-not-deployed-yet-erc-6492). Without the wrapper, a request for an undeployed account fails with a 400.

### Create an Alert Subscription {#alerts-subscribe-to-recovery-requests}

#### `POST /v1/alerts/subscribe`

Create an inactive subscription and send a verification code to the target email address or phone number. Save the returned `subscriptionId` and activate it using `/v1/alerts/activate`.

<Tabs>
<TabItem value="example-request" label="Example Request">

```bash
curl -X POST \
  https://yourcompany.recovery.candide.dev/v1/alerts/subscribe \
  -H 'Authorization: Bearer YOUR_BEARER_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{
  "account": "0x...",
  "owner": "0x...",
  "chainId": 1,
  "channel": "email",
  "target": "user@example.com",
  "message": "siwe(chainId, statement(account, channel, target))",
  "signature": "sign(message)"
}'
```

</TabItem>
<TabItem value="example-response" label="Example Response">

```json
{
  "subscriptionId": "unique-subscription-id"
}
```
</TabItem>
</Tabs>

-   `account`: The Safe account to monitor.
-   `owner`: The Safe owner authorizing the subscription and signing the SIWE message.
-   `chainId`: The supported chain used to verify the owner and signature. Subscriptions cover all supported chains with alerts enabled.
-   `channel`: Either `"email"` or `"sms"` (defines the delivery channel).
-   `target`: The email address or phone number that receives alerts.
-   `signature`: The signature from `owner` over the complete SIWE message.
-   `message`: The complete SIWE message containing this exact statement:

```
I agree to receive Social Recovery Module alert notifications for {{account}} on all supported chains sent to {{target}} (via {{channel}})
```

Replace `{{account}}` with the lowercase Safe address, `{{target}}` with the destination, and `{{channel}}` with `email` or `sms`.

See [SIWE signing](/wallet/recovery/auth-api/#how-to-sign-messages-siwe-eip-4361) to construct the message and signature.

#### `POST /v1/alerts/unsubscribe`

<Tabs>
<TabItem value="example-request" label="Example Request">

```bash

  https://yourcompany.recovery.candide.dev/v1/alerts/unsubscribe \
  -H 'Authorization: Bearer YOUR_BEARER_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{
  "subscriptionId": "unique-subscription-id",
  "owner": "0x...",
  "chainId": 1,
  "message": "siwe(chainId, statement)",
  "signature": "sign(message)"
}'
```

</TabItem>
<TabItem value="example-response" label="Example Response">

```json
{
  "success": true
}
```
</TabItem>
</Tabs>

- `subscriptionId`: The subscription to remove.
- `owner`: The owner signing the request.
- `chainId`: The supported chain used to verify the signature.
- `message`: The complete SIWE message containing the statement below.

```text
I request to unsubscribe from all Social Recovery Module alert subscriptions linked to my account
```

Use this exact statement even when removing one subscription. The `subscriptionId` selects the subscription to remove.


## Error Handling

Use the HTTP status to determine whether a request succeeded. Service errors contain top-level `code` and `message` fields. For example:

```json
{
  "code": 404,
  "message": "Recovery request not found"
}
```

### HTTP Status Codes

| Code | Description |
|------|-------------|
| 200 | Success |
| 400 | Bad Request - Invalid parameters, missing required fields, an invalid guardian signature, a `moduleAddress` the network does not serve, a module not enabled on the Safe or without guardians for it, or new owners the module cannot set |
| 401 | Unauthorized - Invalid or missing Bearer token or API key |
| 403 | Forbidden - SIWE signature verification failed, challenge invalid or expired, sponsorship not enabled for the network, the request is not ready to execute (wrong nonce or insufficient signatures) or finalize, a submission for it is already pending, or the owner cannot manage the subscription |
| 404 | Not Found - Resource not found, or no pending recovery on-chain to finalize |
| 409 | Conflict - The alert subscription already exists |
| 429 | Too Many Requests - IP rate limit exceeded, a second request created for the account within 5 minutes, or the network's sponsorship limit reached for the account |
| 503 | Service Unavailable - The request is not bound to a module yet; retry shortly. Only seen in the seconds after a service restart |
| 500 | Internal Server Error - Something went wrong on the server |

### Troubleshooting

- **Invalid signature:** Check the signing address, chain ID, and exact message or recovery data. A guardian signature must be over the recovery hash of the request's module; an error that names another module means the signature was made for that one, so pass it as `moduleAddress`. SIWE messages must use the statement for the requested action.
- **Module not enabled or no guardians:** The Safe keeps its guardians on the module they were added to. Pass the `moduleAddress` of that module, as listed by `/v1/config/getNetworkConfig`.
- **Invalid or expired code:** Verify that the code matches the challenge ID. If it has expired, create a new alert subscription and verify its new code.
- **Missing resource:** Use the ID returned by the corresponding creation endpoint.
- **Rate limit:** Wait before retrying the request.
