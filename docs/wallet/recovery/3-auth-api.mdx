# Authentication-Based Recovery API (Email / SMS)

Use this API to register an email address or phone number as a recovery method, then obtain a service-managed guardian's signature after the user verifies a one-time password (OTP).

The signature counts as one guardian approval under the account's recovery threshold. Submit it through the [Recovery UX API](/wallet/recovery/ux-api/) to continue recovery.

## Before You Start

- Enable the [Social Recovery Module](/wallet/plugins/recovery-with-guardians/) on the Safe account. Registration also works before the Safe is deployed, with an [ERC-6492 signature](/wallet/recovery/signing/#accounts-that-are-not-deployed-yet-erc-6492); requesting a recovery signature needs the Safe deployed with the module enabled and the service's guardian added.
- [Request service access](https://app.formbricks.com/s/brdzlw0t897cz3mxl3ausfb5) to obtain your service URL and credential.
- Register the recovery method while the user still controls the account. Registrations are specific to an account and chain.

For a TypeScript walkthrough, see [Enable Email/SMS Recovery](/wallet/plugins/add-candide-guardian/) and the [Email/SMS Recovery Flow](/wallet/plugins/recover-account-candide-guardian/).

## Authentication

Replace `https://yourcompany.recovery.candide.dev` with your service URL. Every endpoint lives under the `/v1` prefix. The service is configured with either a Bearer token, sent as `Authorization: Bearer YOUR_BEARER_TOKEN` in every request, or an API key that is the first path segment of every URL. The examples use the Bearer token form; see [Authentication](/wallet/recovery/ux-api/#authentication) in the UX API reference for both.

Registration, registration lookup, deletion, and metadata updates also require a **SIWE message signed by the Safe account**. Verifying an email address or phone number needs no wallet signature. During recovery, the user verifies codes sent to registered channels to authorize the service-managed guardian's signature. See [SIWE signing](/wallet/recovery/signing/#how-to-sign-messages-siwe-eip-4361).

Examples use placeholder addresses, IDs, messages, and signatures. Replace them with values from your integration. Expressions such as `siwe(...)` and `sign(message)` describe values to generate in your application; they are not literal API inputs.

## Integration Workflow

**Set up recovery while the user has account access:**

1. Verify the email address or phone number: call `/v1/auth/verification/request`, then submit the code to `/v1/auth/verification/submit` to receive a `verifiedTargetToken`, valid for 10 minutes.
2. Call `/v1/auth/register` with a Safe-signed SIWE message and the token. The registration is created at once and the response carries the `registrationId` and `guardianAddress`.
3. Add that guardian address to the account's Social Recovery Module on-chain. Registration alone does not add the guardian.

The user enters one code, and the same token registers the target on other chains and [subscribes it to alerts](/wallet/recovery/alerts/#alerts-subscribe-to-recovery-requests) while it is valid. The token is optional: without it, `/v1/auth/register` sends a code of its own and `/v1/auth/submit` completes the registration.

**Recover the account after access is lost:**

If the user does not know the account address, [find it from the email address or phone number](/wallet/recovery/find-accounts/) first. If the account was never deployed, see [Recover Accounts That Were Never Deployed](/wallet/recovery/undeployed-accounts/).

1. Call `/v1/auth/signature/request` with the proposed new owners, their signing threshold, and the `moduleAddress` of the Social Recovery Module the guardian was added to. See [Recovery modules](/wallet/recovery/ux-api/#recovery-modules).
2. Submit verification codes to `/v1/auth/signature/submit` until the response includes `signer` and `signature`.
3. Use that signature to [create a recovery request](/wallet/recovery/ux-api/#create-recovery-request), or [add it to an existing request](/wallet/recovery/ux-api/#collect-a-guardian-signature) with the same recovery data. Collect any other required guardian approvals, execute recovery, and finalize after the grace period.

There are three separate thresholds:

| Value | What it controls |
|-------|------------------|
| `requiredVerifications` | How many channel verifications are needed to obtain the service-managed guardian's signature. |
| Guardian threshold | How many guardian approvals the Social Recovery Module requires to execute recovery. |
| `newThreshold` | How many of the new Safe owners must sign account transactions after recovery. |

## Verify an Email Address or Phone Number {#verify-target}

Prove once that the user controls an email address or phone number and receive a short-lived `verifiedTargetToken`. The token replaces the code step of [registration](#email--sms) and of [alert subscription](/wallet/recovery/alerts/#alerts-subscribe-to-recovery-requests), [lists the accounts](/wallet/recovery/find-accounts/) registered with the target, and asks for a [sponsored deployment](/wallet/recovery/undeployed-accounts/). It proves control of the target, not of an account: registering and subscribing still need their wallet signature.

- Every valid target gets a code, registered or not, and the response is the same for all, so the endpoint does not reveal whether a target is registered.
- The target is normalized: an email address is trimmed and lower-cased, a phone number becomes E.164.
- A request within 60 seconds of the previous one for the same channel and target returns the same `challengeId` and sends no new code.
- A target receives at most 10 codes in 24 hours. Past that, the request returns the latest `challengeId` and sends nothing. The response does not show this, so tell the user to wait when no code arrives.

- A code is valid for 10 minutes and can be used once. A challenge is dead after 5 wrong codes, and every submit for a target is refused once it had 10 wrong codes in 24 hours.
- The token is valid for 10 minutes and can be used several times until then, for example to register the target on two chains and subscribe it to alerts.
- The token is a bearer secret. Keep it in memory, never in a URL, a log, or storage.

| Status | Message | When |
|--------|---------|------|
| 400 | `Target channel '<channel>' is not supported` | `request`: the service has no such channel configured. |
| 403 | `Target is not compatible with the '<channel>' channel` | `request`: the email address or phone number is invalid. |
| 404 | `challengeId not found` | `submit`: no such challenge. |
| 400 | `challengeId already verified` | `submit`: the challenge was already used. |
| 403 | `challengeId has been expired` | `submit`: the code is more than 10 minutes old. |
| 403 | `Invalid challenge` | `submit`: wrong code. |
| 403 | `Too many invalid challenges, request a new code` | `submit`: 5 wrong codes on this challenge. |
| 403 | `Too many invalid challenges for this target, try again later` | `submit`: 10 wrong codes for the target in 24 hours. |

Wherever the token is then used, these two answers apply:

| Status | Message | When |
|--------|---------|------|
| 400 | `"verifiedTargetToken" must be a valid token` | The value is not 43 base64url characters. |
| 403 | `Invalid or expired verifiedTargetToken` | The token is unknown, expired, or issued for another channel or target. |

The token is never accepted by the recovery endpoints. `/v1/auth/signature/request` always sends codes of its own, and a token cannot delete a registration or a subscription.

## Register and Manage Recovery Methods {#auth-registration}

### Register an Email Address or Phone Number {#email--sms}

Register the target as a recovery method for the account on a chain. With a `verifiedTargetToken` issued for the same channel and target, the registration is created at once. Without one, the service sends a verification code and returns a `challengeId` for `/v1/auth/submit`.

#### `POST /v1/auth/register`

<Tabs>
<TabItem value="example-request" label="Example Request">

```bash
curl -X POST \
  https://yourcompany.recovery.candide.dev/v1/auth/register \
  -H 'Authorization: Bearer YOUR_BEARER_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{
   "account":"0x...",
   "chainId": 1,
   "channel":"email",
   "target":"user@example.com",
   "message": "siwe(chainId, statement(channel, target))",
   "signature": "sign(message)",
   "verifiedTargetToken": "43-character-token",
   "metadata": { "label": "Savings" }
}'
```

</TabItem>
<TabItem value="example-response" label="Example Response">

With a `verifiedTargetToken`:

```json
{
  "registrationId": "unique-registration-id",
  "guardianAddress": "0x..."
}
```

Without one, a code is sent to the target:

```json
{
  "challengeId": "unique-challenge-id"
}
```

</TabItem>

    <DataTable items={postAuthRegister} />

-   `account`: The smart account address requesting registration.
-   `chainId`: The chain where the Safe is or will be deployed. Register separately for each chain.
-   `channel`: Either `"email"` or `"sms"` (defines the authentication type).
-   `target`: The email or phone number for authentication.
-   `signature`: A signature valid for the Safe account over the complete SIWE message. For a Safe that is not deployed yet, wrap it as described in [Accounts that are not deployed yet](/wallet/recovery/signing/#accounts-that-are-not-deployed-yet-erc-6492).
-   `message`: The complete SIWE message containing this exact statement:

```
I authorize Safe Recovery Service to sign a recovery request for my account after I authenticate using {{target}} (via {{channel}})
```

See [SIWE signing](/wallet/recovery/signing/#how-to-sign-messages-siwe-eip-4361) for the exact statement and signing requirements.

-   `verifiedTargetToken`: Optional. The token from [`/v1/auth/verification/submit`](#verify-target). The Safe's SIWE signature is still required, with the same statement.
-   `metadata`: Optional. A small object of strings stored with the account on this chain, such as the name the user gave it. The [account lookup](/wallet/recovery/find-accounts/) returns it. See [Account metadata](/wallet/recovery/find-accounts/#account-metadata) for the rules.

The service checks the token before the SIWE message, so a refused token leaves the message unused: send the same signed message again without the token to get a code instead. The token must still be valid when the request arrives. When collecting the signature takes long, for example from the owners of a multisig Safe, sign first and verify the target last.

A target that is already registered for the account on the chain is answered with a 409.

## Obtain a Recovery Signature {#auth-recovery}

### Request Recovery Verification {#request-to-recover-an-account}

Propose new Safe owners and their signing threshold on the module named by `moduleAddress`. The service checks that the module is enabled on the Safe, that its guardian is one of the Safe's guardians on it, and that the module can set the proposed owners (see [Recovery modules](/wallet/recovery/ux-api/#recovery-modules)). It then sends verification codes to the registered channels and returns a `requestId`, the required number of verifications, and the available challenges. The request is bound to that module: the signature returned later is over that module's recovery hash at the account's current nonce on it.

`requiredVerifications` is a majority of the account's registered methods: one for one method, two for two or three, three for four or five, and so on.

An account that is not deployed yet is answered with a 400 that carries `details`:

```json
{
  "code": 400,
  "message": "Account 0x... is not deployed on this network (11155111)",
  "details": { "reason": "account-not-deployed", "sponsoredDeployment": true }
}
```

`sponsoredDeployment` says whether the service can deploy the account. See [Recover Accounts That Were Never Deployed](/wallet/recovery/undeployed-accounts/). [`/v1/recoveries/create`](/wallet/recovery/ux-api/#create-recovery-request) answers the same error.

#### `POST /v1/auth/signature/request`

## How to Sign Messages (SIWE EIP-4361)

Registration, registration lookup, deletion, and metadata updates are authorized by a SIWE message signed by the Safe account. The signing account, the exact statements, and the validity window are on [Signing Requests](/wallet/recovery/signing/).

### Accounts That Are Not Deployed Yet (ERC-6492)

A Safe can register before it is deployed by wrapping its signature with ERC-6492. See [Signing Requests](/wallet/recovery/signing/#accounts-that-are-not-deployed-yet-erc-6492).

## Error Handling

Use the HTTP status to determine whether a request succeeded. Service errors contain top-level `code` and `message` fields. For example:

```json
{
  "code": 404,
  "message": "Could not find registration with this id"
}
```

Errors a client is expected to act on also carry `details`, an object with at least `reason`: the [not-deployed error](#request-to-recover-an-account) and the refusals of a [sponsored deployment](/wallet/recovery/undeployed-accounts/#request-a-sponsored-deployment). Tell them apart by `details.reason`, not by the message.

### HTTP Status Codes

| Code | Description |
|------|-------------|
| 200 | Success |
| 400 | Bad Request - Invalid parameters or missing required fields, email/SMS recovery not enabled on the network, no registration for the account on the chain, the service's guardian not added on the module, a `moduleAddress` the network does not serve, or new owners the module cannot set |
| 401 | Unauthorized - Invalid or missing Bearer token or API key |
| 403 | Forbidden - Signature verification failed, challenge invalid or expired, `verifiedTargetToken` invalid or expired, or action not permitted |
| 404 | Not Found - Resource not found |
| 409 | Conflict - The recovery method is already registered |
| 429 | Too Many Requests - Rate limit exceeded |
| 500 | Internal Server Error - Something went wrong on the server |

### Troubleshooting

- **Invalid signature:** Check the signing address, chain ID, and exact message or recovery data. SIWE messages must use the statement for the requested action.
- **Invalid or expired code:** Verify that the code matches the challenge ID. If it has expired, start a new registration or recovery verification request as appropriate.
- **Missing resource:** Use the ID returned by the corresponding creation endpoint.
- **Rate limit:** Wait before retrying the request.
