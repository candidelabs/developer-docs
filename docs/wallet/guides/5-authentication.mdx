# Signers and Custody

import ThemedImage from "@theme/ThemedImage";
import useBaseUrl from "@docusaurus/useBaseUrl";

A smart account is a contract that does what its owners' signatures authorize. The contract is usually the same open, audited code in every setup, so it doesn't decide whether a wallet is custodial. The owner keys do: who holds them, and who has to take part when they sign.

This page gives a test you can apply to any signer setup, shows how common setups do on it, and ends with the setup we recommend.

## The Test

Ask two questions about the account's owners:

1. **Can anyone other than the user move the funds?** If a third party can produce a valid signature without the user, that party can take the funds, or be compelled to.
2. **Can the user move the funds without anyone else?** If a third party must take part in every signature, that party can stop the user: by choice, by mistake, during an outage, or under legal pressure.

A wallet is non-custodial when the answers are "no" and "yes". Both answers matter. A setup that prevents theft but lets an operator freeze the user still leaves the user dependent on that operator.

These are wallet-level versions of two properties from the [Trustless Manifesto](https://trustlessness.eth.limo/general/2025/11/11/the-trustless-manifesto.html): self-sovereignty, where no one acts on the user's behalf, and the walkaway test, where the user can still act if an operator disappears.

## How Signer Types Compare

| | Onchain passkey | User's own wallet | Key your backend holds | Hosted signing service |
|---|:---:|:---:|:---:|:---:|
| Key held by | The user | The user | Your servers | The provider |
| Only the user can move funds | ✓ | ✓ | ✗ | Varies |
| The user can move funds without anyone else | ✓ | ✓ | ✗ | ✗ |

Some hosted designs need a share the user holds before they can sign, so the provider can't move funds alone. In others, the provider or anyone who gets past its login can. In every hosted design, the provider's servers take part in each signature.

A key your backend holds is the right tool for accounts your app owns, such as a treasury or an automation bot. For accounts that belong to your users, it is custodial by definition.

For [EIP-7702 accounts](/wallet/guides/getting-started-eip-7702/), the original EOA key always keeps full control of the account, so apply the same test to whoever holds that key.

## Onchain Passkeys

Candide recommends onchain passkeys as the main signer for user accounts.

The user's authenticator creates the passkey, and the user signs with Face ID, a fingerprint or the device PIN. The Safe verifies the signature onchain through the [passkey module](/wallet/plugins/passkeys/). No server takes part in signing, including Candide's, so both questions in the test get the right answer.

Passkeys have two tradeoffs:

- A device-bound passkey never leaves the device, so it is lost with the device. A synced passkey survives a lost phone, because the platform copies it, end-to-end encrypted, to the user's other devices. Someone who takes over that platform account can then use it.
- A passkey signs only for the domain that created it (the RP ID). If that domain goes away, so does the passkey's ability to sign.

Both have the same answer: give the user a second way in, as in the [recommended setup](#recommended-setup). As [Vitalik Buterin puts it](https://vitalik.eth.limo/general/2024/12/03/wallets.html), passkeys are "a valuable security gain for ordinary users, but they alone are not strong enough to protect a user's life savings."

See a demo at [passkeys.candide.dev](https://passkeys.candide.dev), and follow the [Passkeys guide](/wallet/plugins/passkeys/) to set one up.

## Hosted Signing Services

Many teams want a login their users already know: email, a social account or SMS. Hosted signing services offer this. They create a key for each user inside their own infrastructure and expose it as an ordinary EOA address, which can be set as the owner of a smart account.

Users get a familiar login and no seed phrase, and designs based on MPC, secure enclaves or cloud KMS mean a single compromised server or employee usually can't extract a key.

What they don't change is who takes part in signing. Running the test:

- **The provider can refuse to sign.** Its servers take part in every signature, so an outage, a terms-of-service decision, a sanctions screen, an acquisition or a shutdown stops the user from transacting. This holds even for designs where the provider can't sign alone.
- **Whoever passes the login can sign.** The user proves who they are with an email link, a social login or an SMS code, and the provider checks it. Anyone who takes over that login can get signatures: through a phished email account, a SIM swap, an insider, or a legal order to the provider. The wallet is as strong as that login.

Some providers describe this setup as non-custodial because no single party holds the whole key. That is a statement about how the key is stored. The test is about what the user can do when the provider stops cooperating. When a hosted key is the account's only owner, the user can't do anything.

## Recommended Setup

A smart account can have several owners and a recovery module, so a key can play different roles in it. For a consumer wallet, we recommend a passkey as the account's single owner, and a [recovery module](/wallet/plugins/recovery-with-guardians/) with three guardians and a threshold of 2.

| Role | Held by | Can | Can't |
|---|---|---|---|
| Owner (passkey) | The user | Move funds. Cancel a recovery. | No restrictions |
| Candide guardian | Candide | Approve a recovery, after a code sent to the user's email | Move funds. Recover the account alone. |
| Wallet guardian | Your backend | Approve a recovery, after a second factor other than email | Move funds. Recover the account alone. |
| Recovery contact | A person the user chooses | Approve a recovery, after confirming the request comes from the user | Move funds. Recover the account alone. |

The two services together meet the threshold, so a user can get back in without asking anyone. Every recovery waits through a grace period, and the owner is alerted and can cancel it. Once the contact is added, recovery no longer depends on either service being available.

The role decides the answer to the test. A service-held key that is the account's only owner, or one of two owners, can move funds or stop the user. The same key as one guardian below the recovery threshold can do neither. The Trustless Manifesto puts it plainly: "Delegation may exist. Dependence must not." See [Set Up Multisig](/wallet/guides/multisig/) for owner thresholds.

[Recommended Setup for Consumer Wallets](/wallet/plugins/recovery-with-guardians/#recommended-setup-for-consumer-wallets) covers when to add each guardian, how to run your own, and which second factor to use.

## Set Up a Signer

- [Passkeys](/wallet/plugins/passkeys/): create a passkey and use it as a Safe owner.
- [External Signers](/wallet/abstractionkit/external-signers): sign with a browser wallet, a hardware wallet or a key your backend holds, through viem or ethers.
- [Manual EIP-712 signing](/wallet/abstractionkit/safe-unified-account/#manual-eip-712-signing-for-a-single-useroperation): compute the hash and format the signature yourself.
